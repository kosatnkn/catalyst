# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

Catalyst (module `github.com/kosatnkn/catalyst/v3`) is a **Clean Architecture microservice template** in Go, not a library. Users don't import it; they generate a new project from it with `new.sh`, which downloads a release tarball and `sed`-replaces every occurrence of `github.com/kosatnkn/catalyst/v3` with their own module path. So:
- Keep the module path written out in full in source files, because the rewrite is a plain text substitution.
- The account feature (`entities/account.go`, `usecases/account_usecases.go`, `persistence/postgres/*`, `rest/controller_account.go`) is **demo code**. It shows the pattern end to end and isn't meant to be complete or correct. For example, the SQL in `account_retriever_postgres.go` is illustrative.
- Reusable building blocks (logger, config parser, Postgres adapter, readiness) live in the separate repo `github.com/kosatnkn/catalyst-pkgs`, not here.

## Commands

```bash
cp config.example.yaml config.yaml   # config.yaml is gitignored; needed to run locally (CI does this too)
make build        # generate metadata, then go build -o main .
make run          # generate metadata, then go run .
make run-with-env # run with CATALYST_* env vars instead of config.yaml
make test         # go test -covermode=count -coverpkg=./... -coverprofile=cover.out ./...
go test ./domain/usecases -run TestName   # single test
make dep-upgrade-all                       # go get -t -u ./... && go mod tidy
```

**Metadata gotcha:** `metadata/read.go` uses `//go:embed` on `metadata/name.txt`, `base.txt` and `build.txt`. These files are generated by `metadata/set_metadata.sh` (from git info and `./metadata.txt`) and are gitignored. On a fresh checkout, plain `go build`, `go vet` or `go test` fails until you've run `make build`/`make run` once, or `./metadata/set_metadata.sh $(pwd)`.

The repo currently has no `_test.go` files.

## Architecture

The layers and the direction of dependencies:

- **`domain/`**: business logic.
  - `entities/`: plain structs.
  - `usecases/`: the logic itself.
  - `boundary/`: interfaces the domain needs, such as `AccountRetriever`, `AccountPersister`, `DatabaseTx` and `Readiness`.

  Use cases depend only on `boundary` interfaces. Persistence implements them (dependency inversion).
- **`infra/`**: lowest-level wiring.
  - `config.go`: the master `Config` struct. Its `mapstructure` tags define the `config.yaml` shape *and* the env var names.
  - `container.go`: a hand-written IoC `Container`.
  - `contracts.go`: the `Logger` and `Readiness` interfaces.
- **`persistence/`**: everything to do with data access. `contracts.go` defines `DatabaseAdapter`. Implementations such as `persistence/postgres/` implement the domain `boundary` interfaces, and all storage details must stay inside this layer.
- **`presentation/`**: outward-facing servers.
  - `rest/`: Gin. `routes.go` registers the handlers. Controllers build their use cases from the container.
  - `telemetry/profile/`: an optional pprof server, toggled by config.
  - `grpc/`, `graphql/` and `websocket/`: placeholders that hold only READMEs.

**Adding a feature, end to end:** add the entity, then the boundary interface(s), then the use case (which takes `*infra.Container` and pulls out the boundary deps). Next, write the persistence implementation and wire it into `Container` and `NewResolvedContainer`. Finally, add the controller and register its routes in `rest/routes.go`.

**Startup and shutdown (`main.go`):** `main` only calls `run()`, which holds the whole startup and shutdown body. The steps run in this order:
1. `config.Parse(infra.Config{}, confSettings)` runs. It takes its defaults from the package-level `confSettings` in `main.go`, and uses the env prefix `CATALYST`. For example, `db.host` becomes `CATALYST_DB_HOST`.
2. `infra.NewResolvedContainer` runs.
3. The servers start.
4. The process blocks until it receives SIGINT or SIGTERM, or until a server reports an unrecoverable runtime error through `Err()`. On any failure (startup, runtime or teardown), `run()` logs it with `logErr` and returns it. Its defers tear everything down, and then `main` exits with code 1. Don't `panic` or `os.Exit` inside `run`.

Each resource is torn down by a `defer` placed right after it's created, so the order of the `defer`s is the shutdown order. Every server follows the same `NewServer`/`Start()`/`Stop()`/`Err()` shape. `Start` fails fast if the listener can't bind, and `Err()` returns a channel that delivers a later serve failure (nil if the server can't fail). When you add a config key, also add a sensible default in the `confSettings.Defaults` map in `main.go`.

**Readiness:** `/readyz` reports on the `Readiness` object built in the container. Components register a checker by their `Identity()` string, for example the DB adapter's ping. To mark a component not-ready at runtime, pipe its errors through `withDBReadinessCheck` (one helper in `persistence/postgres/helpers.go`, another in `domain/usecases/helpers.go`). That helper calls `IsReadinessFail` and then `SetReadiness(identity, false)`. Only pass `Readiness` into objects that need that tracking. A use case that wraps work in `tx.WrapInTx` must also receive `Readiness` and check the transaction error itself.

**Logging:** `infra.FormatMsg` flattens newlines and tabs to keep log lines JSON-friendly. REST handlers don't log errors directly: they call `bindErrorToCtx(ctx, err, status)`, and the logger middleware logs the error.
